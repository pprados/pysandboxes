# Signed-tag release automation (beta phase)

## Goal

Pushing a signed pre-release tag publishes the corresponding build automatically. In this phase nothing reaches
pypi.org: the remote target is test.pypi.org, and a local devpi index is the test bench.

## Decisions

| Topic | Decision |
|---|---|
| Trigger | `push` of a tag matching `v*` |
| Accepted tags | PEP 440 pre-releases only: `^v[0-9]+\.[0-9]+\.[0-9]+(a|b|rc)[0-9]+$`. Any other tag fails with "final release not enabled yet" |
| Tag trust | Annotated tag, SSH-signed, verified with `git verify-tag` against a versioned `.github/allowed_signers` |
| Branch | The tagged commit must be an ancestor of `origin/develop` (of the local `develop` under act) |
| Target switch | Repository variable `RELEASE_TARGET`: unset on GitHub, `devpi` passed by `gh act --var`. Job-level `if:` cannot read the `env` context, so `env.ACT` is not usable there |
| Checks before publishing | `make validate` once, on Python 3.13. `all-tests` is not run in this phase |
| Remote target | test.pypi.org through Trusted Publishing (OIDC), no stored token |
| Artifact signing | PEP 740 attestations, generated by `pypa/gh-action-pypi-publish` |
| Local target | devpi at `http://localhost:3141/$DEVPI_USER/dev/`, reached when the workflow runs under `gh act` |
| Deferred | GitHub artifact attestations (`actions/attest-build-provenance`) and the GitHub release, to be proposed later; final tags and pypi.org |

Why these choices:

- `uv publish` (0.11.16) only uploads attestations that already exist (`--no-attestations`); it cannot generate them.
  `pypa/gh-action-pypi-publish` generates them, and only under Trusted Publishing.
- An API token stored as a GitHub secret would work but is long-lived and produces no attestation.
- `lint.yml` and `test.yml` filter on `branches` only, so a tag push does not trigger them. The release workflow
  runs `make validate` itself; the duplicate run against the `develop` push is intended, since `pip-audit` may turn
  red between the push and the tag.
- devpi's `dev` index is volatile, so the same tag can be replayed locally; test.pypi.org refuses a version twice.

## Components

### `.github/allowed_signers`

One line: `<git user email> <public key of ~/.ssh/id_github.pub>`. Only keys listed here can sign a release tag.

### `.github/workflows/release.yml`

Jobs, each depending on the previous one:

1. `verify`
   - Outside act: `git fetch --force origin "refs/tags/$TAG:refs/tags/$TAG"`, because `actions/checkout` replaces the
     annotated tag with a lightweight one and the signature would be lost. Under act the local `.git` is copied and
     already holds the tag.
   - Fail unless the tag name matches the pre-release pattern.
   - `git -c gpg.ssh.allowedSignersFile=.github/allowed_signers verify-tag "$TAG"`.
   - `git merge-base --is-ancestor "$TAG^{commit}" <branch>`, where `<branch>` is `origin/develop` (fetched first) on
     GitHub and `develop` under act, whose remote-tracking refs are whatever the local clone last fetched.
2. `validate`: `make validate` on Python 3.13.
3. `build`: `uv build`; fail unless the wheel version equals the tag without its `v` (a `.devN` means `hatch-vcs` did
   not see the tag); `twine check dist/*`; upload `dist/` as a workflow artifact.
4. `publish-testpypi` (`if: vars.RELEASE_TARGET != 'devpi'`): environment `testpypi`, `permissions: id-token: write`, download the
   artifact, `pypa/gh-action-pypi-publish` with `repository-url: https://test.pypi.org/legacy/`.
5. `publish-devpi` (`if: vars.RELEASE_TARGET == 'devpi'`): download the artifact, `uv publish --publish-url
   http://localhost:3141/$DEVPI_USER/dev/` with `DEVPI_USER` / `DEVPI_PASS` passed as act secrets.

### Makefile target `release-beta-local`

Next to `github-push-test`. Usage: `make release-beta-local TAG=v0.1.0b1`.

1. Fail unless `TAG` exists in the local repository (it need not be pushed).
2. `devpi-start`.
3. Write `{"ref": "refs/tags/$TAG"}` to a temporary event file.
4. `gh act push -W .github/workflows/release.yml -e <event> --var RELEASE_TARGET=devpi -s DEVPI_USER=$(DEVPI_USER)
   -s DEVPI_PASS=$(DEVPI_PASS)`.
   act uses the `host` network by default (act 0.2.82), so `localhost:3141` reaches devpi.

The user runs this target: Docker is not available to the agent.

## One-time manual setup (maintainer)

- test.pypi.org: declare a pending publisher: owner `pprados`, repository `pysandboxes`, workflow `release.yml`,
  environment `testpypi`.
- GitHub repository settings: create the `testpypi` environment.
- Push `develop` before the first real run: `origin/develop` currently holds a single commit, so the ancestry check
  would reject any tag.

## Error handling

Every failure stops in `verify`, `validate` or `build`, before any publishing job. There is no rollback: a version
published on test.pypi.org is final, and the pre-release lock bounds the impact.

## Testing

Local, through `make release-beta-local`:

| Scenario | Expected |
|---|---|
| Signed tag `v0.1.0b1` on `develop` | Package `0.1.0b1` listed at `localhost:3141/$USER/dev` |
| Annotated, unsigned tag | `verify` fails |
| Final tag `v0.1.0` | `verify` fails with "final release not enabled yet" |
| Signed tag on a commit outside `develop` | `verify` fails |

Then one real run: `git push origin v0.1.0b1`, and check the test.pypi.org project page and its attestations.
