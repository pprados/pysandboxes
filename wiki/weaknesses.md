# Security limits and verified residual risks

## How to read this page

This page summarizes limitations found in the current code and focused probes. Each item names whether the behavior was reproduced or established from code. A reproduced result applies to the tested configuration and environment; it does not prove that all providers or deployments behave identically.

The items were rechecked on 2026-11-13 against release 0.12.0 (commit `2601d77b`). The detailed probes and the commands that reproduced them are in the [Python-layer](audit-python-security.md), [`eval-*`](audit-eval-security.md) and [OS-boundary](audit-native-guard-study.md) assessments.

PySandboxes combines Python API guards with an optional OS provider. Python guards mediate supported Python calls; they are not a boundary against hostile native code in the same process. `none` and `subprocess` do not add a kernel boundary. Kernel-backed providers must be evaluated separately for their platform, kernel, configuration, and exposed host resources.

Detailed evidence and attack paths are in the [Python-layer assessment](audit-python-security.md), the [`eval-*` assessment](audit-eval-security.md), and the [native and OS-boundary assessment](audit-native-guard-study.md).

## OS-provider limitations

- **Landlock cannot filter native UDP — current limitation.** Landlock denies TCP bind/connect by default when ABI v4 is available and opens only configured ports. It has no UDP network rights. The provider is unavailable below ABI v4 rather than running without the default TCP restriction.
- **Landlock allowed opening `/dev/full` for writing — reproduced, impact limited.** The probe only opened the node; it did not write, and the environment lacked `/dev/kvm`, `/dev/dri`, and `/dev/fuse`. This does not establish access to those devices or a privilege escalation. Device nodes present on a deployment and their DAC permissions affect the impact.
- **An unshare ignore-overlay failure can continue — reproduced.** In the tested unshare path, setup continued after warning; user-defined bind-mount failures follow a separate path and are propagated. QEMU and QEMU microvm fail closed on required 9p and ignore-overlay mount failures, covered by fault-injection tests. Startup success alone is not evidence that a requested boundary took effect.
- **DNS stays open as an exfiltration channel — code-established, not reproduced.** The providers that give the sandbox its own network namespace (`unshare`, `bwrap`, `firejail`, `qemu`, `qemu-microvm`, `gvisor`) build their kernel filter with `rule_to_netfilter` (`pysandboxes/netfilter.py`), which always accepts new UDP packets to port 53 of each DNS server of the namespace, whatever the `net=` rules say. The resolver is the slirp4netns one (`10.0.2.3`) for `unshare`, `bwrap`, `qemu`, `qemu-microvm` and `gvisor`, and `unshare` may add the host's upstream servers. The filter does not restrict which names that resolver is asked about. If it forwards to an upstream resolver, as slirp4netns is designed to do (this forwarding was not reproduced), code that encodes data in query names (`<data>.attacker.example`) can send it out through the recursion, even with every `net=` rule denied. The name pinning of [DNS](dns.md) governs what the Python layer resolves; it does not stop native code, a child process or a direct UDP datagram from querying port 53. With `landlock` the same holds for a stronger reason, since it has no UDP right (see above), and `none` and `subprocess` add no network boundary. With `sandbox-exec`, an allowed UDP 53 grants the system resolver socket, which recurses for any name. The channel is narrow in bandwidth and noisy, but nothing in the filter limits or logs it. Treat a profile that denies all outbound traffic as still permitting low-rate DNS exfiltration, and, where this is in the threat model, route the namespace through a resolver that answers only the names of the `net=ALLOW` rules.
- **`net-resolve=runtime` opens an address, not a name — reproduced under `unshare`, `bwrap`, `gvisor`, `qemu` and `qemu-microvm`.** An address learned from an allowed name is open to every process of the sandbox for the TTL (60 s to 1 h), and two names behind one address (a CDN) cannot be told apart: allowing one allows the other on the protocols and ports of its rule. A `DENY` rule that names a host only refuses its resolution: in `pinned` mode it becomes `DENY` address rules placed before the `ALLOW`s, while in `runtime` mode its addresses stay reachable by literal IP, or through another name, wherever a static `ALLOW` CIDR covers them. The filtering resolver is a host-side parser of DNS answers coming from the host resolvers; it is kept minimal and recurses nowhere. The mode exists for `unshare`, `bwrap`, `gvisor`, `qemu` and, as root, `firejail` (the last one not exercised end to end); `pinned` freezes addresses at start and has the opposite limit (a rotating name is refused). Under `subprocess`, `landlock`, `sandbox-exec` and `appcontainer` only the Python guard judges (the kernel layer opens the ports of the name to any host): native code or a child process is not filtered at all, and an address is learned from any resolution the program makes of an allowed name.
- **Landlock cannot enforce `ignore=` rules — code-established.** Its allow-rule model does not hide an otherwise reachable path. The provider warns about ignored paths; when Python guards are disabled, an `ignore=` rule is not an OS-level denial.
- **Landlock does not keep the host's named Unix sockets out of reach — documented, not re-probed for this page.** Landlock filters file access, not `connect()` on a Unix socket, so native code can reach the session D-Bus bus or `/run/docker.sock`; the Python guard still refuses it. From ABI 6 the abstract sockets created outside the sandbox are refused. `bwrap`, `unshare`, `firejail`, `gvisor`, `qemu` and `smolvm` keep `/run` out of reach in their own way; an `expose-ro` or `expose-rw` rule naming a directory under `/run` gives those sockets back. See [Host sockets under `/run`](os-providers.md#host-sockets-under-run).
- **`sandbox-exec` and `appcontainer` cannot filter by host — documented, not re-probed for this page.** Seatbelt scopes a rule to a port, so `net=ALLOW|TCP|203.0.113.7|443|OUT` becomes "TCP port 443, any remote host". AppContainer grants a class of network traffic: it filters no host, port or protocol, and it blocks loopback even when a rule allows it. With the Python guards off, native code reaches any host on an allowed port (`sandbox-exec`) or anywhere in the granted class (`appcontainer`). See [sandbox-exec](sandbox-exec.md#network-limitations) and [appcontainer](appcontainer.md).
- **`firejail` without root cannot open an address while the program runs — documented, not re-probed for this page.** The setuid-root binary puts the jail and its network namespace in the root user namespace, so `net-resolve=runtime` needs the daemon to run as root and a regular user's profile is refused or falls back to `pinned`, depending on the entry point. `firejail` does not run in a container.
- **`gvisor` has no Unix-socket channel to the host — documented, not re-probed for this page.** The guest cannot accept on a handed-down socket and `--host-uds=open` would let it reach host sockets, so `remote-endpoint=auto` stays on TCP. `gvisor` is slower than the namespace providers on system calls (6 to 8 times on a loop of `stat`, `open` or socket calls, measured on one host).
- **A TCG run of `qemu` or `qemu-microvm` carries no KVM isolation claim — documented.** Without a readable `/dev/kvm` the guest runs fully emulated, with no error and no profile change. `qemu-microvm` has at most eight virtio-mmio transports and fails closed when they are exhausted unless the PCIe fallback (`qemu.microvm_pcie`) applies. See [QEMU microvm](qemu-microvm.md#limits).
- **`smolvm`: DNS stays open to the domains a rule allows, and a TCP port is not filtered — measured on smolvm 1.33.0.** The host side of smolvm answers every DNS query itself and filters it by name, so a destination outside the rules does not resolve, but a subdomain of an allowed host does: a program can carry data in the names it looks up, to the authoritative server of that domain. smolvm filters TCP by address only: a rule with a port opens every port of its address, and a port on any address stays closed. A UDP rule keeps its port. See [smolvm](smolvm.md).

See [native and OS-boundary assessment](audit-native-guard-study.md) and [Landlock limits](landlock.md#limits) for details and provider-specific qualifications.

## Python API guards

Python API patching is useful for policy checks and reporting, but code in the same interpreter can reach Python objects that implement or configure those checks. The refreshed [Python-layer assessment](audit-python-security.md) separates demonstrated bypasses from source-based or conditional findings. Among the directly demonstrated cases are mutable file-guard rules and access to already-loaded modules through `sys.modules`; neither result by itself proves a kernel boundary is bypassed.

Known CPython limitations include immutable `object.__subclasses__`, an already-loaded pickle implementation, frame/global introspection, and the immutable C implementation of `pickle.Unpickler.load`. Their exact consequences depend on the guard configuration and execution path. They are documented as limitations of Python-level mediation, not as unexpected failures of the pytest suite: tests marked `xfail` are expected-failure records.

**Modules the daemon imports for itself are not charged to the profile, and are not granted to the application — reproduced by the integration test on 2026-11-13.** The sandbox daemon starts its HTTP server with the guards armed, and arming evicts `sys.modules`, so the server's own imports go through the import guard again. `guard_import.framework_imports()` lets the daemon import them without charging the profile and records each top-level name, because the server imports submodules lazily, per request. The application's own `import` of one of these names is still judged by its `python-import` rules: `tests/integration_tests/test_framework_imports.py` shows `import json` refused with `RuleModuleNotFoundError` (also through a forged `__name__`, `importlib`, a helper module and an async function), granted by a `python-import=json` rule, and recorded by learning. This page said until 2026-11-13 that such an import was allowed without a rule; the test disproves it (11 passed in the project environment, Python 3.14.10). What the exemption does not remove is the `sys.modules` case above: a module the daemon already loaded can be read from the mapping without importing it, and availability of a module is not a right to call its sensitive functions, which `guard_api` still judges. The set, as the test pins it (the union over Python 3.11 to 3.14, since which private companion module is loaded afresh depends on what the interpreter already loaded at startup), is:

`__future__`, `_hashlib`, `_hmac`, `_multiprocessing`, `_queue`, `_socket`, `_thread`, `abc`, `annotated_doc`, `annotated_types`, `annotationlib`, `anyio`, `array`, `ast`, `asyncio`, `base64`, `binascii`, `click`, `codecs`, `collections`, `colorsys`, `concurrent`, `configparser`, `contextlib`, `contextvars`, `copy`, `copyreg`, `dataclasses`, `datetime`, `decimal`, `email`, `enum`, `errno`, `fastapi`, `fractions`, `functools`, `gettext`, `h11`, `hashlib`, `heapq`, `hmac`, `html`, `http`, `importlib`, `inspect`, `io`, `ipaddress`, `itertools`, `json`, `keyword`, `locale`, `logging`, `math`, `mimetypes`, `multiprocessing`, `operator`, `os`, `pathlib`, `pickle`, `platform`, `pydantic`, `pydantic_core`, `pysandboxes`, `queue`, `random`, `re`, `reprlib`, `secrets`, `selectors`, `shlex`, `signal`, `socket`, `socketserver`, `ssl`, `starlette`, `stat`, `struct`, `tempfile`, `textwrap`, `threading`, `time`, `traceback`, `types`, `typing`, `typing_extensions`, `typing_inspection`, `urllib`, `uuid`, `uvicorn`, `weakref`, `zoneinfo`; on Windows also `_ctypes`, `_winapi`, `ctypes`, `msvcrt`, `nt`.

The test fails when the set grows, so this list and the test move together.

Native extensions, `ctypes`, and direct system calls are outside Python wrapper mediation. If such code is within the threat model, use an OS boundary appropriate to the deployment and account for its provider-specific residuals above.

## `eval-*` source execution

The `eval-*` feature parses and checks source strings, rewrites operations, and applies runtime restrictions. Its guarantees and remaining cases are independent of the ordinary Python import/API guards. Consult the current [`eval-*` assessment](audit-eval-security.md) for the parser and runtime boundary, including the scope and prerequisites of any demonstrated issue. Do not infer that an expression is safe solely because `__builtins__` is empty.

## Remote result and exception handling

Remote execution returns serialized results to the trusted parent. Keep `remote-result-mode=data-only` when the application can use the closed supported value set. The optional objects mode uses a restricted reconstruction path, but custom-object support expands the parent-side deserialization surface; see the [transport unpickle guard assessment](transport-unpickle-guard.md) for the result and exception channels.

The exception channel also deserves a separate trust decision: the parent reconstructs exception types that are available in the parent process. The audit documents the conditional side-effect risk for a matching preloaded exception class. This is not evidence that an arbitrary child can import an arbitrary class into the parent.

## Operational guidance

- Use `none` or `subprocess` only when the absence of a kernel boundary is acceptable.
- For native-code threats, select and test a kernel-backed provider on the target host. Confirm effective mounts, network policy, and device exposure rather than relying only on successful startup.
- Keep Python API guards enabled for policy enforcement and useful denials, while treating them as one layer of defense.
- Prefer `remote-result-mode=data-only`; enable object reconstruction only when required by the application.
- Treat any claim as configuration-specific. Re-run probes when changing providers, kernel, guest image, or exposed paths.
